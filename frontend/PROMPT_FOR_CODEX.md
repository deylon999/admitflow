# Задание GPT Sol / Codex: перенести полный AdmitFlow frontend-design-kit

Ты работаешь в существующем репозитории `admitflow`. Рядом лежит распакованный `admitflow-full-frontend`. Это **референс нового дизайна**, но не новая бизнес-реализация. **Не удаляй backend, FSD, API, тесты или историю.**

## Главные требования

1. Дизайн главной: максимально точно воспроизведи `assets/reference-original.png`, используя исходник `src/components/` + `src/styles.css` как старт. Проверь `screenshots/desktop/index.png` против оригинала. Важно: компактные кнопки Header, мягкая тень ForecastCard (CSS `box-shadow` вместо прямоугольной подложки), геометрические кольца/круги внутри нужных контейнеров, плотные секции без ненужного пустого пространства.
2. **Все маршруты:** смотри `SCREEN_INVENTORY.md` и `preview/all-pages.html`. Перенеси не только лендинг, но также каталог, университет, программу, ЕГЭ, прогноз, прогнозные факторы, трекер, списки, конкурентов, сравнение, историю, уведомления, источники, настройки, авторизацию/состояния. UI везде выполнен в одном стиле.
3. Учитывай реальные существующие маршруты и endpoints: новый дизайн адаптируй под них, не ломай API и не изобретай данные или функции. Если такого бизнес-сценария ещё нет, оставляй честное placeholder-состояние, а не фейковую работающую возможность.
4. Компоненты в новой FSD-структуре: `shared/ui` для Button/Card/Badge/Field, `widgets` для Header/Sidebar/ForecastPanel/ProgramList, `features` для AddProgram/Compare/Calculate, `pages` для маршрутов. Используй реальные типы и состояния существующего проекта. **Не копируй `src/pages/AppPages.tsx` одним монолитом** — это демонстрационный исходник, раздели на самостоятельные файлы/секции.
5. **Масштаб 100%:** внешний вид должен быть полноценным при 1440×900 и масштабе браузера 100%. Для исходного лендинга в демонстрации используется CSS zoom 1.25 при ширине >=1200; при переносе лучше перейти к нормальным fluid-значениям `clamp`/grid/spacing tokens и проверить visual regression. На мобильном 390px не должно быть горизонтального скролла.
6. Сделай светлую/тёмную темы там, где их требует текущий проект; у демонстрации полная тёмная тема для внутренних страниц пока не реализована.
7. Зачисти вымышленные маркетинговые утверждения об «90% точности» и любые неподтверждённые показатели. ML-прогноз возможен только при наличии модели и её валидации; показывай источник, дату и неопределённость.

## Проверка и приёмка

- Каждый маршрут рендерится, и нет сломанных ссылок, лишних скроллов, пропадающих кнопок или несоответствия размеров.
- Header и Sidebar общие. Общие компоненты не дублируются по страницам.
- Дизайн главной сверяется со скриншотом `assets/reference-original.png`, а остальные страницы — с `screenshots/desktop` и `screenshots/mobile`.
- Проверь 390, 768, 1024, 1280, 1440px и 100% браузерный масштаб.
- Сохрани гостевые сессии, source provenance, историю и данные текущего проекта, не вводи фиктивные API.
- Гарантии поступления и выдуманные вероятности запрещены.
- Прогони typecheck, lint, unit и browser tests в разумном объёме. На простых CSS правках не надо запускать тяжёлый backend suite.

Порядок: сначала общие токены и Header, затем лендинг, затем app shell, затем внутренние страницы по пользовательским сценариям, потом responsive и QA. Докладывай пользователю, какие страницы перенесены реально, а какие ещё являются демонстрацией.


## Обязательные исправления v3

1. Для всех внутренних страниц применять один layout `AppShell` (desktop sidebar, mobile navigation). Каталоги и аналитика не должны внезапно переходить на оболочку без меню.
2. Не допускается светло-серый текст на красном/синем/фиолетовом. Контраст при обычном и мобильном размерах проверять скриншотом.
3. Не добавлять на каждый экран повторяющиеся плашки про демонстрационный концепт. При этом не выдавать тестовые проценты за ML-результат.
4. График ЕГЭ обязан иметь подпись осей: X — диапазон баллов, Y — доля участников в процентах, легенду годов, читаемую подпись и объяснение. `src/data/demo.ts` содержит **условный** набор долей (каждый год суммируется до 100%). Заменять его реальным источником только после загрузки проверенной статистики.
5. Проверить визуально страницы `/ege-analytics`, `/app/notifications`, `/universities`, `/programs`, `/app/forecast/example` и мобильные версии.
