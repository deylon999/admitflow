# KAN-218 PR4 — цели p95 при 50 запросах

Продолжение [первоначального сравнения](KAN-218-PR4-RESULTS.md). Проверка использует
изолированный PostgreSQL 17.11 с теми же настройками, синтетические 100 000
программ 2027 года, 75 000 архивных программ и 350 000 старых версий фактов.
Нагрузка идёт по настоящему HTTP, с четырьмя Uvicorn workers и 50 одновременными
запросами. Значения синтетические, без национального покрытия и без массовых
связей с конкурсными группами.

## Профиль до изменений

| Сценарий | HTTP p95, мс | Пул, очередь p95 | Checkout p95 | SQL p95 | SQL-вызовов | Создание DTO p95 | Сериализация p95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Первая страница | 473.0 | 179.1 | 205.3 | 119.7 | 7 | 0.27 | 28.7 |
| Вуз и год | 522.9 | 218.9 | 228.2 | 135.7 | 7 | 0.33 | 36.9 |

Это инструментированный Windows-прогон на чистом исходном пути. Checkout включает
очередь, подключение и pre-ping. Количество SQL-вызовов отражает выполнение
курсоров SQLAlchemy. Транзакционные команды и проверка pre-ping измеряются вне
этого счётчика. Время SQL включает передачу результата до возврата драйвера.
Отдельные p95 нельзя складывать. Задержки одного worker доминировали в хвосте;
серия исходного поиска прервалась на прогреве по клиентскому таймауту. Два
завершённых профиля сохранены.

Объединённое чтение снизило число SQL-вызовов для первой страницы до 2, для
обычного вуза с годом до 1. Первый вызов в глобальном сценарии обслуживает
два отдельно проверяемых архивных профиля. Один SQL-оператор возвращает текущую
политику, точные метаданные, выбранные ключи и их полезную нагрузку в том же
REPEATABLE READ snapshot. Фильтр по вузу вне архивного набора пропускает чтение
архивных строк. DTO и порядок сортировки сохраняются.

Профиль CPU затем выявил повторное построение SQL и поиск идентификаторов
в неизменяемых справочниках. SQL-формы переиспользуются с параметрами запроса.
Индексы справочника живут вместе с объектом конкретного снимка. При смене
снимка рассчитываются заново. База и результат запросов не кешируются.
CPU-время фасада в профиле упало примерно с 10 до 3 мс для первой страницы
и с 7 до 1–2 мс для вуза с годом. Завершающая оптимизация выбирает только
используемые в ответе поля и агрегирует количество и годы за один проход.

## Точный поиск

Тестовый запрос по коду `09.03.04` даёт 64 500 совпадений. 50 прогретых SQL-
измерений на вариант показали следующую стоимость точного COUNT.

| Вариант | p50, мс | p95, мс | План |
| --- | ---: | ---: | --- |
| Обычный strpos | 28.1 | 37.4 | Parallel Seq Scan |
| LIKE с доступным pg_trgm | 63.3 | 78.1 | Parallel Seq Scan |
| Транзакционный счётчик | 0.71 | 0.76 | Индекс по коду и году |

Принудительное использование GIN заняло 79,4 мс, а индекс добавил 47,8 МиБ.
Для столь частого запроса индекс требует прочитать большую долю таблицы.
Тестовый pg_trgm не входит в production-схему.

Миграция `0016` поддерживает точные количества по вузу, году и одиночной
ASCII-подстроке формы `dd.dd.dd`. Считаются вхождения во всём прежнем тексте
поиска, включая встроенные и перекрывающиеся окна. Повтор в одной программе
учитывается один раз. Другие токены и запросы из нескольких слов используют
прежний точный путь. Архив считается отдельно в том же snapshot.

При смене видимости statement-триггеры составляют дельты по OLD/NEW строкам.
Они выполняются в той же транзакции, что и публикация, под существующей
сериализацией writers. Проверены откат, конкурентные изменения, карантин и
выход из конфликта, смена политики, изменение поискового текста. Счётчики
сверены с независимым разбором литералов и полным исходным SQL.

Backfill на 175 000 текущих строк занял 14,2 с. 50 замен ревизии на 100
программ и парные rollback-тесты измеряют относительную цену записи.
Операция на 50 документах на исходной ветке была отменена после примерно
109 секунд. Сравнимый пакет из 10 документов (1 000 программ) выполнялся
в отдельном ограниченном прогоне. В парной проверке с одинаковыми входами
медиана одной замены выросла с 58,2 до 66,4 мс, пакета с 3,58 до 3,64 с.
Размер таблицы счётчиков с индексом
составил 1,10 МиБ. Накладные расходы приемлемы для измеренного профиля.
Два конкурентных writer и rollback сохранили точные итоги, а регрессия
дополнительно проверила смену текста и восстановление видимости после конфликта.

## Проверка HTTP и CI

Два прогретых прогона на исходной Windows-среде использовали Node HTTP,
четыре Uvicorn workers, 50 одновременных HTTP-запросов и одни и те же настройки
PostgreSQL 17.11. `work_mem=4MB`, `shared_buffers=128MB`, `max_connections=100`.
Скрипт дожидался старта четырёх процессов и прогревал те же сокеты, на которых
потом измерял задержки. До замера в каждом сценарии полный HTTP JSON сверялся
с независимым исходным SQL. Во время нагрузки сверялся точный `total`.
SHA измерений `7e00bf30ae6bfc64a740f4b995f29420a4ca1aee`.

| Сценарий | Цель p95 | Замер 1 p95, мс | Замер 2 p95, мс |
| --- | ---: | ---: | ---: |
| Первая страница | <200 мс | 142,7 | 137,4 |
| Вуз и год | <150 мс | 137,1 | 109,4 |
| Код | <300 мс | 156,2 | 149,6 |
| OFFSET 99 988 | <500 мс | 316,4 | 338,3 |
| OFFSET 50 000 | <500 мс | 289,4 | 292,1 |

В измеренных фазах 63 723 запроса и 0 ошибок. Пиковая загрузка PostgreSQL
достигла 927% CPU, рабочий набор держался около 1,22 ГиБ. Счётчик временных
записей вырос на 139 380 200 байт. Одинаковый прирост после исходного SQL в
сценарии вуза может включать отложенный сброс статистики проверки, поэтому
сумму нельзя приписать одному HTTP-пути. Обе глубокие страницы использовали
тот же точный OFFSET-контракт. Полный JSON, включая пустые ответы, архив и
поиск, покрыт также PostgreSQL-тестами.

Ранние испытания с Python HTTP-клиентом и непрогретыми соединениями дали
больший разброс и иногда транспортные ошибки. Один из ранних Windows-прогонов
уложился в p95, но зафиксировал восемь таймаутов для OFFSET 50 000. Повтор
без прогрева дал 215 мс для первой страницы. В двух Linux-прогонах с
HTTP-клиентом в той же сетевой среде p95 фильтра по вузу составил 169,5
и 167,1 мс при цели 150 мс. Результат относится к измеренной конфигурации.

Все согласованные p95 выполнены в двух прогретых Windows-прогонах.
