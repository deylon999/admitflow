# B20/T221: очистка старых private данных при сбросе

Исправлена F02 из [аудита](b19-frontend-audit.md). До изменения четыре
браузерные проверки воспроизводили старые карточки/данные печати после
успешного либо прерванного сброса. Проверки выполнялись на отдельном
SQLite API8032 с синтетическими владельцами и управляемыми ошибками/задержками.

Во время reset private запросы отключаются, карточки, история, черновик,
сравнения, счётчики и печатный отчёт скрываются. Это отдельное состояние
ожидания, не ложное сообщение об истечении сессии.

После завершения reset, включая error path, старые запросы отменяются ещё
раз, а private query entries удаляются. Инвалидация старого watches.data
больше не переносит его в новую сессию при503. Актуальные данные появляются
только после нового авторизованного чтения; ошибка не выдаётся за пустой
список. Если DELETE не прошёл, серверная запись сохраняется и снова видна
после свежего чтения. Изменение владельца во время завершения reset не
переводится обратно в active старым callback.

Проверены четыре сценария в Chromium и Firefox:

1. DELETE/создание новой сессии успешны, новый GET/watches возвращает503:
   старых карточек/history/print данных нет, показана ошибка загрузки;
   повтор восстанавливает корректный пустой список.
2. Старый GET/watches задержан до сброса и завершён после него: старая
   карточка не возвращается, включая данные скрытого печатного DOM.
3. DELETE/session возвращает503: cached copy скрыта; фактическая серверная
   запись остаётся и возвращается только после свежего авторизованного GET.
4. DELETE успешен, POST новой сессии возвращает503: прежние данные скрыты
   уже во время ожидания; после ошибки нет старых карточек/печати/счётчика,
   нет лишнего DELETE и ложного pending→expired сообщения.
