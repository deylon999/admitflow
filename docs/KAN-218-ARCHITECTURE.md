## 2. Технический план до изменения кода

Целевая кампания — **2027**. Цель — минимум **471 из 785** головных вузов
при сохранённом знаменателе реестра от 2026-11-10. Новый официальный срез
может изменить знаменатель только после отдельной проверки. Архив 2026
учитывается исключительно в 2026 и совокупной истории. Пока не проверены
публикации вузов, отсутствие данных 2027 нельзя назвать доказанным отсутствием
публикаций. Получение 60% и полнота каталогов внутри вузов — разные показатели.

### Последовательность небольших PR

1. **Этот PR: идентичность и совместимое хранение.** Добавить версионированные
   функции ключей с unit-тестами; Program и две таблицы связей с ограничениями
   университета/уровня/кампании. Новая миграция 0013 после 0012; ни одного
   переименования или backfill опубликованных групп. Проверить upgrade на
   заполненной 0012 в изолированном настоящем PostgreSQL, metadata alignment,
   сохранение старого API и истории. Это основа хранения, не публикация фактов.
2. **Проверенный импорт нескольких вузов.** Сначала паспорт источника,
   доступ/robots/rate policy и оригинал с SHA256; независимая сверка программы
   и связи с конкурсами. Сохранять document revision (university, campaign year,
   original/final URL, document type, publication date или null, fetched/checked,
   extractor version, raw/normalized hash, validation/review/publication states).
   Факты и каждую M:N связь привязать к этой версии. Отдельная новая миграция
   для provenance и staging/published revision: она нужна после проверки
   реальных документов, не подгонять их под ParsedList. Публиковать атомарным
   указателем проверенную ревизию набора; подтверждать изменения мест как
   новую версию факта, конфликт идентичности оставлять на review. Существующие
   catalog_lock/RawStore/fetcher переиспользовать; SourceSnapshot/CandidateEntry
   не трогать. По одному источнику ошибку журналировать отдельно от rollback.
3. **Массовый импорт.** Конечная очередь документов, дедлайн/размер, ограниченная
   параллельность и частота на домен, ограниченные retries/backoff/Retry-After,
   checkpoint по хешу и версии extractor; отдельный результат для каждого
   источника. Не повторять отказ 401/403/challenge обходным способом.
4. **Масштабирование API.** SQL WHERE/order/count/offset/limit; counts и years
   агрегацией, без CatalogProgram для всех строк на HTTP. Кэш справочника
   организаций сохраняется. Индексы под измеренный план и нагрузку; fixture
   масштаба явно synthetic и никогда не публикуется как реальный каталог.
5. **Покрытие.** Расширить KAN-221 по targetYear=2027: уникальные Program и
   CompetitionGroup, головные вузы, регионы/уровни, отдельные филиалы и годы,
   completeness=partial/complete/unknown, ошибки/кандидаты/конфликты. Отсутствие
   подтверждённого полного перечня означает partial/unknown, не complete.
6. **Приёмка.** Независимая выборка оригиналов разных вузов/регионов/форматов,
   PostgreSQL и frontend состояния, полная регрессия/CI на SHA, итоговый отчёт,
   owner review. KAN-218 остаётся незавершённой до фактических 60% за 2027.

После каждого PR — review и merge владельцем, затем следующий от нового main.
Автоматического merge нет. T312–T321 фиксируют шаги; частичный результат не
переводит всю KAN-218 в In Review. Авторизация, дизайн v3, CI workflows и
production-конфигурация вне текущего изменения.

### Идентичность v1

- University: использовать существующий подтверждённый ID (включая legacy
  aliases и registry-only). Филиал имеет собственный ID; parent не выводится
  из имени/домена. Новые функции не создают ID университета.
- Campaign: существующий ID сохраняется; для новых — UUIDv5 от версии,
  university_id, year и level. Найденная по unique tuple существующая кампания
  имеет приоритет над вычисленным ID. UUID не служит доказательством источника.
- Program: отдельная сущность уровня university/level. Начальная идентичность
  — UUIDv5 от university, level, **origin campaign_id**, source namespace и
  ключа, проверенного в документе. По умолчанию годовая область; совпадающий
  официальный номер в другом году сам по себе не доказывает тождество.
  Связать существующую Program с новой кампанией можно после явной сверки
  официальной преемственности. Origin campaign остаётся неизменным.
- Source namespace — однажды утверждённое имя семейства источников внутри
  вуза, не текущий URL, parser version или дата загрузки. Ключ сохраняется
  буквально: регистр/ведущие нули значимы; surrounding whitespace/control
  characters отклоняются. Нормализация названий/кодов — для фактов и поиска,
  не автоматического объединения идентичности.
- Group: существующие ID и official_id неизменны. Для нового конкурса UUIDv5
  от campaign_id, namespace, проверенного ключа, формы, финансирования и
  категории. Если официальный ID не стабилен — source key является
  каноническим JSON-массивом проверенных discriminators (например, code,
  profile_id, campus_id); название само по себе недостаточно. Два конкурса с
  одинаковым набором discriminators — неоднозначность, а не одна запись.
  Неизвестные условия/ключ не позволяют вычислить подтверждённый group ID.
- В v1 источник должен подтвердить форму/финансирование/категорию; неизвестное
  остаётся в staging и не создаёт фиктивный конкурс. Program может существовать
  без CampaignProgramGroup связей. Места не входят в ключ: это изменяемый факт,
  null не равен нулю. Изменение формы/финансирования/категории при том же
  официальном номере — конфликт, требующий review, не переименование старой
  группы и не автоматическая публикация новой вместо неё.

Program хранит origin campaign, namespace/key и уровень; CampaignProgram
связывает её с кампаниями того же вуза/уровня. CompetitionGroupProgram
связывает конкурс с одной или несколькими программами **в той же кампании**.
Одна программа может иметь несколько конкурсов, а также ни одного. Код,
название, места и provenance относятся к ревизиям фактов, которые будут
добавлены в PR2; эти три таблицы сами не дают статуса verified/public.

Для SQL integrity нужны дополнительные unique constraints на
Campaign(id, university_id, level), Program(id, university_id, level) и
CompetitionGroup(id, campaign_id); composite FK не даёт связать разные вузы,
уровни или годы. Новые связи RESTRICT, без cascade удаления истории.
Миграция не создает Program из каждой старой группы: это было бы
неподтверждённым соответствием 1:1. Новая схема не меняет старые pointers.

### Контракт KAN-223 и передача KAN-227

Старые endpoints/DTO в PR1 сохраняются байт-в-байт по полям и семантике.
Пример существующей записи: `id=sgu-2026-4588`, `campaignId=sgu-2026-bachelor`,
`year=2026`, `studyForm=full-time`, `funding=budget`, `category=general`,
`seats=16`, provenance.kind=`archive` (проверено по reviewed manifest).
Приведённый пример не вводит новый контракт.

До PR2 нужно согласовать с deylon999 представление самостоятельной программы,
неизвестных условий и нескольких конкурсов. Предлагаемый минимальный вариант
для обсуждения: сохранить legacy public id и добавить отдельные programId и
competitionGroups с реальными groupId; standalone Program требует nullable
условий либо согласованной иной проекции. **Это предложение, не реализованный
или согласованный контракт.** Без решения не публиковать фиктивные группы
и не менять строгий frontend decoder. Запрос на согласование должен содержать
реальный проверенный образец из первого набора PR2.

KAN-227 использует существующие CompetitionGroup.id и Campaign.id, связывая
списки через Source.group_id. Новые M:N связи добавляют смысл без смены этих
ID. Реестр соответствий внешнего list ID и group ID требует проверенных
атрибутов кампании; совпадения названий недостаточно. В PR1 не добавляются
parser персональных строк, snapshots, ranks, consent, subscriptions или ML.

### Риски и способы проверки

| Риск | Проверка/ограничение |
| --- | --- |
