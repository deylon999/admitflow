# KAN-218 — этап 4: производительность публичного каталога

Начальная точка: `main@1e7693e`, 22 ноября 2026 года. PR31 с пакетным
импортом объединён; затем объединены изменения архитектуры backend, scripts
и frontend. Работа выполняется в отдельном worktree, без изменения других веток.

## План и критерии

1. Аудит существующей SQL-проекции, контрактов, индексов и тестов.
2. Воспроизводимый baseline на настоящем PostgreSQL: 100 000 текущих программ,
   несколько кампаний, головные организации и филиалы, предыдущие ревизии.
3. Оптимизация только по результатам замера, без изменения DTO и идентичности.
4. PostgreSQL/API-регрессия: total, years, фильтры, Unicode и буквальные символы
   поиска, порядок, страницы, конфликты, исторические данные и согласованный snapshot.
5. Измерения после изменения, EXPLAIN, память, документация, PR и CI на точном SHA.

Acceptance T319: HTTP-запрос материализует только выбранные факты и связи,
поиск/count/пагинация выполняются в SQL; на репрезентативном наборе сохранены
правильные ответы, старые URL/ID СГУ, unknown/null, карантин конфликтов и
изоляция кампаний. Отдельно измеряются задержки, число запросов, число загруженных
ORM-объектов и пиковая память Python. EXPLAIN включает actual/buffers.
Локальный ориентир p95 чтения — 500 мс без нагрузки; это не приёмка staging
под конкурентной нагрузкой из общей DoD. Порог фиксируется до замера.

Все массовые записи синтетические, находятся только в disposable PostgreSQL
и не являются источниками или доказательством национального покрытия.
Исходные документы и работающая БД не используются. Цель 2027 остаётся 471/785;
её достижение относится к последующим этапам.

## Аудит

`product_catalog.py` уже выполняет SQL-фильтрацию и гидратацию выбранной страницы.
Программы и конкурсные группы не переписываются. Два оконных счётчика исключают
неоднозначный public ID и повторную публикацию одной программы в кампании.
Они вычисляются до фильтров и повторно для years, total и page. Поиск использует
Python casefold при записи/запросе и буквальный substring через escaped LIKE.
Legacy slice ограничен проверенными профилями СГУ. Вузы берутся из проверенного
справочника; агрегаты программ читаются из той же SQL-проекции.

Существующие индексы facts начинаются с revision_id либо public_id. Перед
добавлением индексов или миграции требуется baseline и EXPLAIN. Применённые
миграции не редактируются. Условия исключения конфликтов и REPEATABLE READ
для ответа сохраняются. Frontend, авторизация и workflows вне изменений PR4.

## Реализация и результат

Код `b19dd7a`, чистая копия в начале финального замера. Проверка конфликтов
использует anti joins текущих verified-публикаций по public ID и паре
program/campaign. Ключи сравниваются глобально, до условий пользовательского
запроса; неоднозначные записи исключаются с обеих сторон. Исторические ревизии
не участвуют. Модель идентичности и правила подтверждения не изменены.

Общий CTE используется для years, total и выбранных ключей в одном statement.
Метаданные возвращаются отдельными строками, поэтому пустая страница не теряет
total или years. Гидратация читает только выбранные факты и явные M:N связи.
Поиск программ при выборе вузов объединён с агрегацией количества и кампаний,
вместо повторного просмотра проекции для каждого поискового токена.

| Сценарий | Было p95, мс | Стало p95, мс |
| --- | ---: | ---: |
| Первая страница | 1196,5 | 661,4 |
| Кампания2027 | 1145,4 | 606,3 |
| Вуз и кампания | 1174,4 | 259,1 |
| Код | 1203,7 | 758,8 |
| Избирательный поиск | 1201,1 | 628,1 |
| Пустой поиск | 1227,1 | 603,3 |

Для всех восьми сценариев совпал SHA полного DTO-ответа, включая порядок,
пагинацию, total, years и provenance. Число SQL statements на непустую
страницу8→6 (включая benchmark SET LOCAL timeout), пустую6→4. Python peak
1,77→1,49MB; facts загружаются только для выбранной страницы, в том числе
при limit50. Полные широкие оконные сортировки заменены проверками конфликтов;
получение точного total всё ещё требует обработки текущего набора в PostgreSQL.

### Проверки и практические ограничения

Добавлены проверки пустых facets/deep pages, Unicode casefold и буквальных
символов LIKE, нескольких токенов в разных программах вуза, ограниченной
гидратации257 программ, конфликтов между разными вузами/годами, а также явного
повторного использования программы в другой кампании. Существующие проверки
REPEATABLE READ, замены публикации, неизвестных условий, общих конкурсов и
старых URL сохранены.

Повторная проверка сохранённых официальных оригиналов на `b19dd7a` прошла:
[реальный API/import report](evidence/kan-218-pr4-official-api.json).
Повторный импорт unchanged, архивные ответы СГУ сохранены,2027 содержит две
программы ВШЭ. Это пилот1/785, а не национальный охват.

**Ориентир p95 500мс не достигнут во всех массовых сценариях.** Он не снижен
после измерения. Результат PR — измеренное ускорение примерно1,6–4,5 раза и
ограниченная память HTTP-запроса. Staging под конкурентной нагрузкой не проверен;
gate производительности не принят. Глубокий OFFSET и глобальная проверка
конфликтов остаются затратными. Существующая граница offset100000 сохранена,
новых ограничений количества организаций/программ не вводится.

Итоговый CI и точный SHA фиксируются в описании PR, чтобы добавление самого
результата в файл не создавало ещё один непроверенный коммит. Review/merge
выполняет владелец; T319 остаётся review, KAN-218 и цель471/785 не завершены.

## Baseline

Код `7dcd24f`, чистая рабочая копия на старте замера. PostgreSQL17.11,
work_mem4MiB, 100000 текущих синтетических программ, 200000 предыдущих facts,
4000 документов, 785 головных организаций и 215 филиалов; дополнительно два
проверенных legacy профиля СГУ. Нормальные ограничения и триггеры включены.
Каждый сценарий: прогрев и 9 измерений без tracemalloc; отдельный запрос для
пиковой памяти/ORM и отдельные EXPLAIN ANALYZE BUFFERS. Задержки включают
SQLAlchemy/Pydantic и loopback Docker, без внешней сети и конкурентной нагрузки.

| Сценарий | p95, мс |
| --- | ---: |
| Первая страница | 1196,5 |
| Кампания2027 | 1145,4 |
| Вуз и кампания | 1174,4 |
| Поиск по коду | 1203,7 |
| Избирательный поиск | 1201,1 |
| Пустой поиск | 1227,1 |
| Глубокая страница | 1408,1 |
| Обратный порядок, 50 записей | 1117,6 |

Пиковая память Python около1,77MB; загружено не больше размера страницы facts.
Два глобальных WindowAgg сортируют текущие100000 строк; сортировки используют
external merge/Disk. Для первой страницы три повторных проекции стоят примерно
347/342/491мс в EXPLAIN, то есть проблема в повторной работе SQL.
