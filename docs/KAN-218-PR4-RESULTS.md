# KAN-218 PR4 — результаты отдельной адаптации

Адаптация находится в `feat/kan-218-read-model` поверх полного backend-дерева `9ad69c6`.
На дату измерений `main` оставался на `6fdafc9`. PR #38 находится в `main`, остальные
этапы до #42 объединены в родительские ветки. PR #43 остаётся draft, пока
владелец не интегрирует backend-цепочку. См. [план](KAN-218-PR4-READ-MODEL.md)
и [описание проекции](KAN-218-READ-PROJECTION.md).

Измерения используют PostgreSQL 17 и синтетический каталог из 100 000 текущих
программ кампании 2027, 75 000 программ кампаний 2024–2026 и 350 000 предыдущих
версий фактов. Источник, предметные DTO и идентичность сохраняются. Число вузов
с официальными данными зависит от опубликованного набора и измеряется отдельно.
Синтетические программы не добавляют массовых связей с конкурсными группами.
Поэтому измерения характеризуют поиск, подсчёт и пагинацию, а стоимость ответа
с большим числом связанных групп покрыта проверками корректности и требует
отдельного нагрузочного профиля.

## Что изменилось

- Источником истины остаются неизменяемые ревизии и указатель текущей публикации.
  Проекция хранит ключи, текст для поиска и порядка, видимость и точные счётчики
  по вузу и году. Триггеры обновляют их в транзакции смены указателя, пересчитывая
  глобальную допустимость затронутых ключей. При несоответствии версии справочника
  API читает исходные таблицы через точный SQL.
- Первая и конечная страницы используют короткие индексные сканы. Для OFFSET
  выбирается ближайший конец с опорой на точный `total` в том же snapshot.
  SQL ограничивает отсортированный результат до объединения с двумя архивными
  строками СГУ. Порядок, две ориентации сортировки и пагинация сохраняются.
- Без поиска `total` суммирует точные счётчики. Поиск буквальной подстроки
  сохраняет точный `COUNT`. Условия поиска, регистр Unicode и экранирование
  сверены с исходным `LIKE`. Программы и связанные конкурсные группы
  гидратируются только для выбранной страницы.
- Новая миграция `0015` содержит backfill и обратное удаление производных объектов.
  `ANALYZE` на backfill и после крупных публикаций улучшает оценки PostgreSQL.
  Индекс документа ускоряет замену ревизии. Миграции `0001`–`0014` сохранены.

## Цена альтернатив

Исходный SQL проверяет конфликты через anti-join. Материализованный CTE повторно
используется в подсчёте и странице, но создаёт большой промежуточный набор. Индексы
исходных фактов занимают место и обслуживаются при записи истории. Они помогают
только в тех частях плана, где условия поиска или порядка доступны планировщику
до CTE. Предварительно построенная таблица текущих строк уменьшает работу
соединений, но сохраняет проверку конфликтов на каждом чтении. Прототип с готовой
допустимостью переносит эту работу из запроса, однако оставляет сканы для точных
`COUNT` и facets. Оба прототипа заморожены на время опыта.

В планах первой страницы и кода PostgreSQL не выбрал добавленные исходные
индексы. В первом сценарии сам план записал 51 090 временных блоков в обоих
вариантах. Сортировки первой страницы при этом выполнились в памяти, включая
`top-N heapsort`. Основной объём временных данных здесь связан с глобальной
обработкой промежуточных строк. У глубокой страницы дополнительно дорогой
OFFSET. Измерения хранят планы и счётчики отдельно для каждого запроса.

Полный refresh materialized view при каждой публикации повторяет глобальную
работу и увеличивает время записи и блокировку. Отложенный refresh вводит окно
устаревания. Транзакционная проекция поддерживает только затронутые записи и
точный `total` в том же snapshot ценой индексов, триггеров и сериализации записи.
Курсор мог бы исключить скан пропуска по центру набора, но требует отдельного
совместимого API. Его поведение нельзя подставить вместо точного публичного OFFSET.

## Воспроизведение

Запуск из корня Python с backend-зависимостями создаёт собственный контейнер и
временную схему. Исходные базы не используются.

```text
python scripts/qa/benchmark_catalog_serving.py --workers 1 4 --output test-results/kan218-read/serving-final.json --compare-output test-results/kan218-read/alternatives-final.json
python scripts/test_postgres.py tests/test_program_read_projection.py tests/test_program_publication_api.py tests/test_product_catalog.py tests/test_migration_metadata.py tests/test_migrations.py
```

В HTTP-прогоне используются реальный Uvicorn на loopback, 10 прогревочных запросов
на сценарий, затем параллелизм 1, 10, 25 и 50. Каждая фаза длится не менее 10 секунд
и содержит не менее 50 отсчётов. 50 фасадных вызовов и `EXPLAIN (ANALYZE, BUFFERS)`
измеряются отдельно. Docker CPU и working set относятся только к PostgreSQL.
`pg_stat_database` даёт дельты buffers и temp files с возможным лагом сброса
статистики. Время Python и его пиковые аллокации измеряются отдельно.

порядка и точного `total` с исходным SQL для обеих сортировок.

Точный подсчёт частого кода по-прежнему сканирует набор.

На запись синтетического набора ушло 367.1 с, включая 185.0 с на INSERT 4000 указателей. ## Граница достигнутой производительности

Четыре workers укладываются во все ориентиры при 10 одновременных запросах.
При 25 запросах ориентир превышен для частого кода, при 50 — для первой
страницы, вуза с годом и кода. Обе глубокие страницы укладываются в 500 мс
при 50 запросах. При этом OFFSET из середины читает примерно половину
годового индекса и расходует больше CPU PostgreSQL, чем конечная страница.

Для первой страницы и фильтра по вузу увеличение числа workers улучшило
задержку и пропускную способность при низкой загрузке CPU PostgreSQL.
Измеренный предел относится к связке Windows, Docker и серверного процесса.
Проверка большего числа процессов на Linux может отделить предел приложения
от ограничений TCP на тестовой машине. Замеры поиска показывают другой предел.
Для часто встречающегося кода возвращаются 64 500 совпадений из 100 000, а
отсортированная страница использует индекс и читает только выбранные ключи.
Основная работа приходится на точный подсчёт совпадений и достигает примерно
14 из 16 логических CPU PostgreSQL. Обычный B-tree по полному коду меняет
семантику, поскольку текущий поиск ищет также подстроки названия и вуза.
Индекс подстрок в проекции может помочь редким запросам, но для частого
совпадения нужен замер стоимости широкого чтения и записи индекса.

Для более строгого SLA при 50 запросах возможны отдельно проверяемые меры.
Объединение коротких запросов чтения уменьшит число обращений из приложения.
Параметр точного совпадения по коду может дать индексируемый поиск для клиентов,
которым нужна эта семантика. Целевые подсчёты для заранее определённых запросов
потребуют поддерживать точные агрегаты в транзакции и отдельно доказывать
совпадение с прежней подстрокой. Эти варианты оставляют текущий контракт
доступным и требуют собственных замеров перед изменением API.
