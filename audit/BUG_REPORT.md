# Подтверждённые дефекты

Проверяемая версия: `ad5b938`, 2026-11-08. Номера строк ниже относятся к этой
версии (`git show ad5b938:<path>`), если явно не указано иначе. Исправления и
ограничения повторной проверки уточняются в FIX_REPORT.md.

## AUD-01 — High — очистка чужих каталогов backup (Fixed)

`scripts/backup_production.sh:33`. `find ... -type d -mtime ... -exec rm -rf`
не отличает резервные копии от пользовательских каталогов. При запуске с общим
output-каталогом удаляет любой старый подкаталог. Ожидание: удаляются только
завершённые копии, принадлежащие скрипту. Воспроизведение: отдельный временный output
с устаревшим каталогом user-documents; проверка retention не должна его трогать.
Введено `609d4b7`. Исправлено: формат/UUID/manifest, точный набор файлов,
запрет symlink и удаление только известных файлов без recursive delete.

## AUD-02 — High — удаление фиксированной проверочной БД (Fixed)

`scripts/backup_production.sh:22–24`. `dropdb --if-exists admitflow_restore_check`
удаляет уже существующую БД, которую текущий запуск не создавал; параллельные запуски
мешают друг другу. Воспроизведение безопасно через command double с отказом createdb:
до исправления dropdb выполняется до createdb. Ожидание: уникальное имя, удаление
только после успешного создания своей БД. Введено `609d4b7`; исправлено UUID и finally.

## AUD-03 — Medium — исправный dump отвергается при текущих записях (Fixed)

`scripts/backup_production.sh:16,23,29`. pg_dump и source-counts читают разные снимки.
Добавление/удаление записи между ними приводит к ложному backup_verification_failed.
Ожидание: проверка согласованного dump, не сравнение с изменяемой live-БД.
Введено `609d4b7`. Исправлено: pg_restore --exit-on-error, инвентаризация восстановленной
БД и проверка её raw references; количество строк не заявляется сравнением с live-БД.

## AUD-04 — High — отсутствующий raw-файл не мешает verified=true (Fixed)

`scripts/backup_production.sh:17–18,35`. `tar -tf` проверяет читаемость списка архива,
но не наличие и хеш объектов из source_snapshots. Читаемый tar с отсутствующим
или повреждённым объектом объявлялся проверенным; replay после восстановления невозможен.
Введено `609d4b7`. Исправлено: SELECT references из восстановленного dump и SHA-256
каждого обычного tar member; symlink и дубликаты отклоняются, извлечения файлов на диск нет.
Регрессии: test_raw_archive_verifies_referenced_content_without_extracting,
test_completion_and_database_ownership[raw].

## AUD-05 — Medium — monitoring принимает неудачную копию за успешную (Fixed)

`scripts/ops_check.py:46`, `scripts/backup_production.sh:26–30`. restored-counts.txt
создаётся до сравнения и остаётся при отказе. Monitoring использовал его наличие и
mtime каталога как доказательство свежей проверенной копии. Ожидание: учитывать только
успешно завершённые копии. Введено `609d4b7`. Исправлено атомарной публикацией manifest
после всех проверок; дата читается из verifiedAt. Отдельный тест частичной копии.

## AUD-06 — Medium — timeout диагностики обрывает формирование сигнала (Fixed)

`scripts/ops_check.py:20–23,31`. TimeoutExpired, отсутствующая docker-команда и
невалидный JSON не перехватываются: main не формирует JSON проблемы и не достигает
webhook. При report=None также теряются независимые disk/backup alarms.
Введено `609d4b7`. Исправлено преобразованием отказа в api_status_unavailable
и независимыми проверками диска/backup. Регрессии ошибок subprocess и JSON.
Доставка реального webhook не проверялась и не выполнялась.

## AUD-07 — Medium — Windows pytest не собирается (Fixed)

`backend/app/worker.py:10`. Безусловный `import resource` вызывает 12 collection errors
на документированном Windows-окружении. Введено `e63f5a5`; до ветки импорт отсутствовал.
Воспроизведение: backend/.venv/Scripts/python.exe -m pytest -q.
Исправлено ленивым импортом в limit_memory: тесты и библиотечный API доступны,
worker CLI на Windows явно требует Docker, лимит не отключён молча.

## AUD-08 — High — отложенный reset удаляет заменившую сессию (Fixed)

`frontend/src/lib/api.ts:117–133`, `lib/query-client.ts:25` (точный поиск: resetSession,
markSessionFailure). Сброс ждёт Web Lock без проверки исходного sessionEpoch;
поздний 401 заменяет changed на expired, подталкивая ко второму DELETE новой сессии.
Это предшествующий дефект, не введён десятью коммитами zarbondo.
В main исправлен `1c38475`; здесь воспроизведён заимствованными unit-регрессиями:
5 failed / 10 passed до исправления. Ожидание: устаревшая операция прекращается,
синхронизация читает сессию под тем же lock и сохраняет changed при позднем 401.

## AUD-09 — High — старые карточки после смены владельца (Fixed)

`frontend/src/pages/TrackerPage.tsx:167–185`. После DELETE+создания новой сессии старый
watches cache только invalidated. При 503 повторного чтения React Query сохраняет
старые данные: они могут попасть в карточки, сравнение и печать новой сессии.
Ожидание: cache старого владельца удалён независимо от результата последующего GET.
Предшествующий дефект; исправлен в main `3494ed6`. В audit ветке проверяется отдельным
реальным API/E2E с инъекцией 503 только после reset.

## AUD-10 — Medium — отменённые поля возвращаются из черновика (Fixed)

`frontend/src/components/DirectionForm.tsx:42–45`. Эффект сохраняет только dirty;
возврат к начальному значению не удаляет предыдущий sessionStorage draft.
Воспроизведение: в пустой форме ввести и стереть вуз, либо изменить и вернуть rank,
перезагрузить — предлагается восстановить отвергнутые значения.
Предшествующий дефект; main `b2cd2c4`. Подтверждён на ad5b938: 3 E2E fail,
1 pass; остальные 9 остановлены --max-failures=3. Скриншоты сохранены отдельно.
Исправление должно сохранять retry key неопределённого сохранения и первоначальный TTL.
