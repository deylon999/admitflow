# Постоянный контекст проекта «Абитуриент»

Структура: `frontend/` — React, все npm-команды выполняются из него; `backend/` — Python API; `shared/calculations.json` — общие fixtures TS/Python; `docs/` — спецификация и память; `scripts/` — инструменты плана. Проверять roadmap из корня репозитория. Макеты лежат в `docs/design/`.

Git: небольшие осмысленные коммиты с английскими сообщениями Conventional Commits (`feat(api): ...`, `fix(web): ...`, `test: ...`, `docs: ...`, `ci: ...`). Использовать настроенное авторство пользователя, не менять его глобальные настройки. Репозиторий: https://github.com/deylon999/admitflow. Не переписывать опубликованную историю без явного запроса.

1. В начале сессии читать `docs/STATE.md`, `docs/ROADMAP.md`, карточку текущей задачи в `docs/TASKS.md`, релевантные решения и последние записи `docs/LOG.md`.
2. Выполнять `python scripts/roadmap.py --check` и `python scripts/roadmap.py --next`. Проверять реальные файлы и Git status; команды предыдущей сессии могли выполниться частично.
3. TASKS.json — единственный реестр статусов; STATE.json — точка продолжения; LOG.md — история. TASKS.md и корневой CHECKLIST.md генерируются скриптом. После каждого законченного шага обновлять статусы и выполнять --render; отмечать [x] только для done, частичные/review/blocked оставлять [ ].
4. Держать одну задачу `in_progress`. Перед реализацией проверить зависимости, назначить currentTask, сформулировать проверку. Не начинать заново уже проверенный шаг без нового основания.
5. Для done нужны acceptance, общая Definition of Done и evidence. Наличие кода, старого dist или ожидаемого deployment URL не доказывает готовность.
6. Перед завершением обновить TASKS/STATE, добавить запись LOG, выполнить `--render` и `--check`. Передавать конкретный следующий шаг, частичные операции, процессы и ограничения без секретов.
7. Правила расчёта, сезона, состава группы и смысла согласий менять вместе с DATA_RULES.md и тестами. Не превращать сценарии в гарантии и неподтверждённые вероятности.
8. Ручной режим, архив, свежий импорт и неподдержанный источник должны быть различимы. Цель национального покрытия не означает уже достигнутого покрытия.
9. Изменения пользовательских требований отражать в PRODUCT/DECISIONS/TASKS, не стирая старую историю. Приоритет у текущих указаний пользователя.
10. Эти правила не требуют дополнительных согласований обратимых действий. При внешнем блокере зафиксировать причину и условие снятия и продолжить независимую задачу.
